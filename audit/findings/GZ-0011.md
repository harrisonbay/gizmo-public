# GZ-0011: published dusty-wave profile collapses grain timesteps

- Status: confirmed
- Confidence: high
- Affected configuration: `GRAIN_FLUID`, `GRAIN_BACKREACTION`,
  one-dimensional non-self-gravitating dusty wave
- Oracle: byte-pinned public-profile regression

## Evidence

The hosted `dustywave_ics.hdf5` contains 64 gas particles and 64 type-3
grains, but it does not contain a grain `SmoothingLength` dataset. The public
parameter file leaves both suggested softening prompts commented out.

The grain Courant criterion obtains its length from `Get_Particle_Size(p)`.
With no type-3 softening, that length is zero and the requested grain timestep
is therefore zero. Unless `STOP_WHEN_BELOW_MINTIMESTEP` is enabled, the code
warns and substitutes two integer timebase ticks rather than failing.

In a one-rank reproduction, the 64 gas particles selected time bin 45 while
all 64 grains selected time bin 1. After 2,532 synchronization points the
simulation time was only `1.098079960293319e-14`, versus a requested terminal
time of `2.5`.

## Reproducible profile

Enabling the public file's own `Softening_Type3 0.001` prompt makes all 128
particles select time bin 45. The corrected-C run then completes 32,768
synchronized steps, reaches `t=2.5`, and matches the supplied `t=1.2` dust
velocity curve to `0.0751%` peak-normalized RMS. Its complete profile and
reduced state tables are pinned under `validation/oracles/dustywave`.

This prompt is a workable recovery, but it is not uniquely specified by the
published test. Upstream should either enable the required parameter, include
the intended positive grain numerical size in the IC, or fail explicitly
instead of silently entering a practically non-advancing run.
